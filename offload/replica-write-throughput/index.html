Can a replica keep up with a primary's full write rate over one connection?

No, not in general. For small writes the replica keeps up with everything the primary does, but only because attaching a replica costs the primary itself 30-45% of its rate: the primary's main thread spends about 36% of its time building the replication stream. For 512 B values the replica's own read and apply path is the limit, and for 4 KB values the single TCP connection caps the stream at about 1.17 GB/s on both builds.

Regression on superset-frontier: MSET of 10. Frontier's replica applies MSET on its main thread (92% busy, IO threads ~19%) at 167 MB/s, against upstream's 278 MB/s. It keeps up only to 165k/s at pipeline 16 (0.24 of its primary's max), against upstream's 271k/s. The idle IO threads suggest parallel apply does not cover MSET; a replica-side profile was not taken.

Reading the evidence

  • primary main The primary's main thread is at ~100% while the replica keeps up, and attaching the replica alone takes 30-45% off its rate. In the upstream profile propagateNow / replicationFeedReplicas take ~36% inclusive, mostly growing and copying the stream buffer (_sdsMakeRoomFor, sdscatlen, zrealloc_usable, memcpy). The replication socket queues stay small.
  • single TCP connection Every SET 4 KB catch-up probe, on both builds, and frontier's SET 512 B probes apply at exactly 1,192 MB/s (9.5 Gbps) while no replica thread is saturated. At the SET 4 KB limit the stream is 1.14-1.17 GB/s and the primary's Send-Q holds 3-4 MB. The NIC's aggregate limit is far away; 10 Gbps is the EC2 per-flow cap inside a cluster placement group.
  • replica Upstream's replica reads the whole link on one IO thread (100% in every io-threads-on cell); at SET 512 B its main thread is at 95% and its catch-up rate equals its keep-up limit. Frontier's SET 512 B limit is replica-side (a 4-core replica lowers it, the primary is unchanged) but no single thread is pinned. Frontier's MSET limit is its main thread.

Step-up rate vs replication lag and output buffer

Open-loop fixed-rate holds of 60 s, stepped up ×1.25 toward the primary's max, then bisected. "Lag" is the offset gap: master_repl_offset on the primary minus the replica's processed offset, in bytes. "Output buffer" is the primary's output buffer for the replica (omem); the soft limit is 64 MB for 60 s, the hard limit 256 MB. A failing step shows a growing gap, a growing buffer, then a disconnect and a full resync. Only cells where the replica fell behind at some rate are listed. The gap carries ±a few MB of noise from aligning two hosts' sample clocks.

Method and caveats

Builds

Hosts and core layout

  • c8g.metal-24xl (Graviton4), us-east-1c, one cluster placement group. Each rig is three hosts: a load generator, a primary and a replica, with one standard replication link (a single TCP connection) between them. Three rigs ran in parallel; every cell ran on one rig.
  • 8 cores per server, primary and replica identical. Cores are total CPUs the server may run on (NIC IRQs, main, IO threads and housekeeping), not main + IO threads.
    • io-threads on: 3x irq, main, 3x io, aux (io-threads 4).
    • io-threads off: 3x irq, main, 4x aux.
    • Smaller-replica variant: 4-core replica irq, main, io, aux (io-threads 2).
    NIC IRQs are spread over the irq CPUs; bio and jemalloc threads go to aux; each thread is pinned and checked.
  • Replication: client-output-buffer-limit replica 256mb 64mb 60, repl-backlog-size 10mb, diskless sync, repl-disable-tcp-nodelay no, no compression.
  • Load: memtier_benchmark, 32 threads × 16 clients = 512 connections, 1M-key random keyspace. SET 64 B / 512 B / 4 KB; HSET (64 B value); "INCR mix" = INCR + HINCRBY 1:1; MSET of 10 keys × 64 B. Pipeline 1 and 16. Rates are commands/s (one MSET = one command).

Per cell (build × workload × pipeline × io-threads)

  1. Primary max: primary alone, closed-loop saturation, 3 × 20 s.
  2. Attached: replica attached and caught up, then closed-loop saturation, 3 × 60 s.
  3. If the replica fell behind at saturation: open-loop fixed-rate steps (×1.25) from the last passing rate toward the primary max, 60 s holds, two bisections, then the highest passing rate held 3 × 60 s and the first failing rate 2 × 60 s.
  4. Catch-up probe: replica paused during a 25 s saturating load, then resumed; its apply rate while catching up (3 reps).

Keeps up = over a 60 s hold the offset gap does not grow (slope < 0.5% of the stream rate) and ends small, the primary's output buffer for the replica does not trend up, the replica is never disconnected and never full-resyncs, and the primary serves ≥ 90% of the offered rate. Offsets, lag in bytes and seconds, output buffer, per-thread CPU, socket queues and NIC counters were sampled every second on both nodes.

Caveats

  • Frontier MSET of 10 is a regression (see the callout above): its replica is slower than upstream's on this workload, so frontier replica numbers should not be quoted for multi-key writes until it is fixed.
  • The 10 Gbps single-connection cap is the EC2 per-flow limit inside a cluster placement group. Outside one the per-flow limit is 5 Gbps, so the SET 4 KB ceilings would roughly halve.
  • Frontier SET 64 B, pipeline 16, io-threads on: the replica kept up at full saturation (~2.87M/s) in 2 of 3 reps; the third had one disconnected sample, so the table uses 2.63M/s, the highest rate that passed all 3.
  • Frontier SET 512 B, pipeline 16: the limit is on the replica side, but which part of the frontier replica (IO hand-off vs apply lanes) is the long pole was not isolated.
  • The first sweep sized its fixed-rate steps from the attached saturation rate, which a resync storm drags down, and under-stated 8 cells. Those cells were re-run with the ladder above; the tables use the re-runs, and the step charts show both.
  • superset-new-prefetch was not run.
