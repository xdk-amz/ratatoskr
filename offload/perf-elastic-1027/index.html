Summary

A Valkey node that scales vertically while it scales out goes from a small CPU budget to a larger one under load, then back. This page runs that on one server: 60 s steps of 2 → 3 → 5 → 3 → 2 total CPUs under sustained load, with CONFIG SET io-threads changed together with the CPU set at every step. A separate sweep picks the keyspace-shard-bits value that gives superset's write lanes their throughput. Cores on this page are total CPUs the server may use, including the CPU that takes the NIC interrupts.

CPUs removed without telling Valkey

io-threads stays at 4 while the CPU set shrinks 4 → 2 → 1 server CPUs and grows back (5 → 3 → 2 → 3 → 5 total CPUs). This is a container that loses CPU quota with no operator action. SET P16, 2 reps.

keyspace-shard-bits sweep

Superset only (fixed io-threads per cell, no core changes). The keyspace has 2bits shards and a key's write lane is its shard number mod the lane count, so bits 0 means one lane and no parallel writes. Generator ops/s, median of 3 reps. A cell is worse when its median is more than 5% below the best arm's and every rep is below the best arm's slowest rep. Cells marked not server-bound hit the NIC limit or had main below 80% busy, so they do not separate the arms.
Default chosen: 8 bits for every standalone server, including at io-threads 1.
  • 0 bits loses 17-51% on writes at 3 and 5 total CPUs. A node started at 2 CPUs with auto (which resolves to 0 there) never gets write lanes when scaled up.
  • 4 bits loses 6% on SET at 4 total CPUs (3 IO threads): 16 shards spread unevenly over 3 lanes.
  • 10 bits is 0.5-2% behind 8; 12 bits is 3-5% behind 8.
  • Any bits above 0 costs 2-3% at 2 total CPUs, P16, which is below the 5% bar. SET P1 shows no cost.
  • Memory (local): 8 bits adds 15 KB to an empty server and nothing per key; 14 bits adds about 1 MB.

Method and core layout

Cores
Total CPUs the server may run on: N server CPUs plus 1 CPU for NIC interrupts. Nothing the server needs runs elsewhere and no generator runs on the server host. CPUs outside the layout only run idle housekeeping.
Layouts
Threads
Main, the IO threads and bio float over the N server CPUs (taskset on the whole process), as they would inside a container with N CPUs. io-threads = N at every step except "CPUs removed", where it stays at 4. Each step applies the new CPU set and CONFIG SET io-threads together, under load.
Hardware
c8g.metal-24xl (Graviton4), one server host and two generator hosts per pod. Timelines, CPUs removed and soak ran on one pod in us-east-1d; the shard-bits sweep on a second pod in us-east-1c. Generators within 0.10-0.15 ms of their server.
Load
memtier, 128 B values, 1M keys, uniform. P16: 2,304 connections. P1: 9,600 connections. 80/20 = 80% GET, 20% SET. Closed loop: offered load is set by connection count and pipeline depth, not by a rate.
Builds
Measurement
Timelines: server-side ops/s each second (total_commands_processed); a step's level is the median of its steady seconds. Shard bits: generator completions in a 10 s window. Builds alternate in every rep. A 5 ms PING probe from the generator host measures stalls.
Transitions
"Worst dip" is the lowest second in the first 5 s of a step divided by the lower of the two levels it joins. "Change" is how long the CPU-set plus io-threads change took to apply.

Caveats

  • This emulates small nodes on a 96-CPU metal host with a 40 Gbps NIC. A real 2- or 4-vCPU instance has its own network and packet limits, so absolute numbers on the metal rig are upper bounds for small instances.
  • The IRQ CPU is counted in "cores" but is never used by the server's threads, so 2 total CPUs means one CPU for all of main, bio and the event loop.
  • From 2 to 3 total CPUs superset's writes barely scale (SET P16 1.14x, 80/20 1.27x), and upstream is ahead on writes there. That is the cost the staged write lanes add to every write command at 2 IO threads. It is open work.
  • SET P1 levels off at 0.43-0.46M at 5 total CPUs on every build, upstream included. The cause is not identified; it may be the generator's connection count rather than the server.
  • At 2 total CPUs, 9,600 P1 connections arriving at once delay the first INFO by 14 s on superset and 15.5 s on upstream, while PINGs stay under 45 ms. This happens before any core change and is shared with upstream.
  • MSET of 10 hit the NIC's inbound allowance in the shard-bits sweep, and the 9-CPU cells were not server-bound; both are shown but do not separate the arms.
  • Superset here runs --io-threads-free-on-bio yes --main-read-batch yes, which are off by default on that commit. "Auto shard bits" is bug B: it resolves to 0 at io-threads 1 and is fixed by making auto resolve to 8.
