Server-counter ops/s, median of 5 reps per cell on each host. Spreads, client-reported rates and latencies are in the sections below.
  • Pipelined read (10 requests in flight per connection): superset wins. It serves 1.4M (c6gn) and 4.4M (c7gn) more ops/s than Dragonfly in stock, and 5.4M and 6.9M more in the tuned layout, at a lower p50 and p99. Likely reason: superset's IO threads parse and answer a whole batch of GETs from one socket read, so its fixed cost per loop pass is spread over ten times as many commands. Dragonfly's 48 threads are 97-99% busy here (1-2% of the host idle), and it gets slower, not faster, when given 32 threads with interrupts kept away (8.50M to 7.85M on c7gn). That points to a per-command cost in Dragonfly that batching does not remove.
  • Write (one request in flight, 1200 connections): superset loses. In stock it serves 2.1M (c6gn) and 2.9M (c7gn) fewer ops/s; in the tuned layout 1.3M and 1.9M fewer. Likely reason: every superset loop pass goes through its main thread, which sits at 100% in every cell, while half the host is idle in stock (50% on c6gn, 49% on c7gn). With one request per connection each pass carries few commands, so main's fixed work per pass sets the rate. Dragonfly has no such central thread: each of its threads owns its own connections and runs at 96-100%. The tuned layout, which moves NIC interrupt work off the server threads, more than doubles superset's writes (0.82M to 1.93M on c6gn, 1.27M to 2.82M on c7gn) and gains Dragonfly 11-14%.
  • Read (one request in flight): superset loses, by less. 1.2M and 1.3M fewer ops/s in stock; 0.36M and 1.5M fewer tuned. Reads are answered on IO threads without running on main, so main does less per command than for writes, but it is still at 100%.
  • Tail latency. Superset's p99.9 is 8.5-18 ms in every cell; Dragonfly's is 0.5-2.2 ms. The p99 values are close (under 2 ms for both, except superset stock writes on c6gn at 17 ms). This run did not profile the cause.
  • Our Dragonfly is representative. On c7gn our memtier numbers are 1.04x, 0.85x and 1.08x Dragonfly's published ones. On c6gn they are 0.82-0.89x. By Little's law, though, our c6gn runs sustain more requests per second than the published runs' own latencies allow (write: 3.20M against 3.05M), so the c6gn gap is in how memtier totals its threads, not a slower Dragonfly. See the check.
  • c6in.12xlarge, the third server on Dragonfly's page, had no EC2 capacity for the whole window (start retried every 2 minutes for 90 minutes), so it is not on this page.

Method

  • Server rate. A script on the server reads total_commands_processed (INFO stats, which both systems serve) every 0.2 s during each test. The rate is the commands from 10% to 90% of the test's total, divided by the time between those two points. It leaves out connection setup and the tail where memtier threads that finished early stop sending load.
  • Client rate. memtier's "Totals" Ops/sec. memtier averages each thread's own rate, so threads that finish early count at their full rate. That puts it above the server's steady rate, more so when per-thread rates vary.
  • Latency. memtier's Totals p50, p99 and p99.9, median over reps (min-max in Every rep).
  • Layout capture. At every server start: every server thread's name and CPU, every NIC queue interrupt's effective CPU, irqbalance state and the server's command line, recorded per server, config and system under layout in data/dragonfly-fresh.json.
  • Hosts. One server host per instance type, used for both systems, with no other work on it; one client host per server. No result on this page comes from another host or another day.
