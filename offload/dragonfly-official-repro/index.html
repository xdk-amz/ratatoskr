Verdict

  • Reproduction. Dragonfly v1.15.0 with Dragonfly's own commands lands within 10% of its published numbers in 6 of 9 cells. The outliers are c6gn write (0.83x), c6gn read (0.88x) and c6in write (1.28x). By the published latencies (Little's law, 1200 connections over the average latency), our runs carry more load than Dragonfly's in every non-pipelined cell, so the shortfall is in how memtier reports Ops/sec, not in the server (see Reproduction gap).
  • Superset at io-threads 48 (one thread per vCPU, as Dragonfly runs) is limited by its main thread: main sits at 100% while the 47 IO threads idle at about 60%. Against our measured Dragonfly it reaches 0.27-0.29x on writes, 0.38-0.45x on reads, and 0.89-1.04x on pipelined reads.
  • Superset at io-threads 24 is the best setting in a sweep on the same 48-vCPU servers. Against our measured Dragonfly: pipelined read 2.1-2.6x faster (20M ops/s on c7gn and c6in, at less than half the latency), read 0.63-0.92x (closest on x86 c6in), write 0.38-0.52x.
  • Superset loses every non-pipelined cell at 1200 connections, and write is the largest gap (1.35-2.40M SET/s against Dragonfly's 3.5-5.4M). The write gap profile traces it to the length of superset's lock-step loop iteration, not to CPU cost: turning on the epoll thread and keeping NIC interrupts off the server's CPUs lifts writes to 0.72x Dragonfly on c7gn and 0.86x on c6gn, with no code change.

  • memtier's Totals Ops/sec is above its own wall-clock average in every Dragonfly write and read run (for example c6gn write: 3.47M reported, 3.26M = 240M requests over the run's wall time). Each memtier thread finishes its 4,000,000 requests at a different time, and the summary rate is built from per-thread rates, so it overstates the rate at which the server was actually serving.
  • The published rows show the same pattern: 1200 connections over the published average latency gives 3.05M for c6gn write, well below the 4.20M reported. On that common basis our Dragonfly runs are 7-8% above the published c6gn numbers and 2% above the published c6in write.
  • The run is server-bound, not client-bound: the client was 47% idle during c6gn reads, and raising connections from 1200 to 1800 and 2400 added only 4-6% at higher latency.
  • No ENA allowance counters (bandwidth, pps, conntrack) were exceeded on the server. Server CPUs were about 82% busy each, with 20-30% of that in softirq for the network.
  • Remaining differences we cannot control: the exact memtier build and the c6gn/c6in host generation behind each instance type. The page does not state either.

Write gap profile

Why superset trails Dragonfly on the official write test, and what closes it. Superset build: superset-frontier at 4056df343 (a later tip than the 29152861a used above), with the same client, servers, OS, placement and memtier write command (1200 connections, one request in flight each). Rates here are wall-clock: the server's command counter over a clean 12 s window, not memtier's Ops/sec, which reads high (see Reproduction gap). Rep 1 of each config was profiled and is excluded; the numbers are the clean reps after it (3 for the first c7gn configs, 2 for the rest). No code was changed for any of these runs.

The bottleneck

Superset is not short of CPU. It spends about the same CPU per command as Dragonfly (9.8 µs against 9.4 µs), but half or more of the 48 vCPUs sit idle while main is 100% busy. Its write rate is set by how long one loop iteration takes. Each iteration runs poll, read, write and reply as separate phases, and every phase waits for its slowest thread before the next one starts. At io-threads 24 on c7gn one iteration takes about 615 µs and serves about 1000 commands. Three things make it that long:

  • Main waits in epoll on its own. Main calls epoll_wait over roughly 1000 ready sockets every iteration. That takes 110-200 µs, and no IO thread works during it.
  • IO threads park and are woken every iteration. The poll step outlasts the time IO threads spin before sleeping, so they sleep every iteration and main has to wake them again: 73k context switches/s at io-threads 24 and 174k/s at 48. The wake-up costs 67-118 µs per iteration.
  • NIC interrupt work lands on the server's own threads. irqbalance puts the NIC's 32 receive queues on 32 of the 48 CPUs, and server threads running there handle network receive work inline (18% of main's samples). The thread that gets the most of it finishes its phase last, so each phase takes 1.7-2x as long as the average thread needs.

Writes themselves are not the limit: every SET ran on the IO-thread lanes with no serial fallback, and the write phase is 8-15% of each iteration. io-threads 48 is slower than 24 because twice as many threads park and wake each iteration, and a thread interrupted by network work holds up everyone else.

Config key

  • io-threads N: the repro setup, threads unpinned, irqbalance on.
  • + epoll thread: io-threads-epoll-thread yes, the epoll thread on its own CPU. It counts toward N (main, N-2 IO threads, epoll thread).
  • + NIC IRQs off server CPUs: irqbalance stopped, the 32 NIC queue IRQs spread over CPUs N to 47, main on CPU 0, each IO thread on its own CPU below N.
  • + both: both changes together. In every config the server uses at most 48 CPUs, as Dragonfly does.

What would close the gap, ranked

All of these stay within one unified staged loop: no second loop, and no keyspace reshard when thread counts change.

At the best measured point (c7gn, io-threads 32 + both) an iteration is 128 µs for about 475 commands, IO threads spend 15-23% of their samples waiting at phase barriers, and main is 98% busy. Changes 2-5 target that remaining wait.

Reproducing this

  • Provision both sides from the Ubuntu 23.04 AMI, point apt at old-releases.ubuntu.com, build memtier 2.0.0, unpack Dragonfly v1.15.0, make superset at the SHA above.
  • Per rep: start the server, run write, read, pipelined read in that order, shut it down. Server per-CPU utilisation was captured with mpstat during each test.
  • Raw per-rep numbers: data/results.json.
