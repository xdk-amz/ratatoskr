Summary

This page shows where superset-frontier stands on write throughput at small CPU counts, at commit 29152861a. It compares superset with upstream Valkey on SET, HSET, 80/20 (80% GET, 20% SET), MSET10 and GET, with clients pipelining 1 command (P1) or 16 commands (P16). Two cases are covered: a server started at the CPU count measured, and a server that was scaled up to it under load with CONFIG SET io-threads. Cores on this page are total CPUs the server may use, including the CPU that takes the NIC interrupts. Every number comes from runs made during the write-scaling loop; nothing was rerun for this page. Cells whose data needs a rerun to be trusted are marked as such.

The two kept fixes

Both are on the fork's superset-frontier, fast-forwarded on top of the epoll thread-budget work: e13f63f2f → 35b537e81 (fix 1) → 29152861a (fix 2). Neither changes throughput for a server started at its final size (within 0.985-1.007x of the build before it, at 2, 3 and 4 total CPUs), and neither moves the pinned 1, 8 and 16 core layouts by more than 1.6%.

Fix 1: an allocator arena per IO thread (35b537e81)

jemalloc decides how many arenas to create from the CPUs the process may use when it starts. A server started on 1 server CPU gets a single arena, and IO threads added later by CONFIG SET io-threads share it with main and wait on its locks. Each IO thread now binds to an arena of its own when it starts, and reuses it when its slot restarts. Diagnosis on one binary, SET P16 at 3 total CPUs: started there 1.68M; scaled up from 2, 1.47M; scaled up with 8 arenas forced, 1.67M; scaled up with the fix, 1.66M.

Fix 2: clients in the middle of a command move to the IO threads (29152861a)

On a scale-up, a client moved from main onto the IO threads only when it was between commands. With 16 pipelined MSETs of about 1.5 KB each, main's read of a connection nearly always ends partway through a command, so those clients stayed on main for good and MSET10 did not scale at all. A client may now move with a command still arriving, because the IO thread resumes the same parser state. Diagnosis: MSET10 P16 after scaling 2 → 3 total CPUs, 0.31M → 0.46M commands/s.

Where the time goes: MSET10 P1 at 3 total CPUs

perf record on the server CPUs while both are fully busy, one run per build, converted to CPU nanoseconds per MSET10 command. Superset uses 11.65 µs per command and upstream 9.69 µs; at P16 the two are about equal (6.1 vs 6.2 µs). The extra is spread over several places, and no single item is above about 7% of samples.
  • Lane key prefetch: superset's keyspace bucket is 660 ns higher. The hashtable lookups themselves (findBucket) cost the same on both builds; the difference is the write lanes' key prefetch, about 600 ns per MSET against about 250 ns for upstream's prefetch.
  • Allocator slab refills: 7% of samples. They come from allocating each value string while parsing (createStringObject → arena_cache_bin_fill_small → edata_heap_remove_first), on main and on the IO thread. From P16 to P1 superset's allocator cost grows by about 750 ns per MSET while upstream's falls by 280 ns.
  • Staged-loop bookkeeping: read events per client, claims on the shared poller and waits at the barrier, about 670 ns more at P1 than at P16. Upstream's main + one IO thread hand-off costs 666 ns in total.

Tried and rejected

Settings on the 29152861a binary at 3 total CPUs (and 4 where stated), 3 reps, against the same binary with defaults and against upstream. None was kept. The lane prefetch run finished its P1 cells only.
Also tried, one rep each, not tabulated: larger jemalloc thread caches (lg_tcache_nslots_mul 3 and 4, tcache_nslots_small_max 2048) moved both superset and upstream by 0 to +1.6% on MSET10 P1 at 3 total CPUs.

Open options

No option has been chosen. They are listed in no order of preference.
A. Use upstream's IO-thread loop below a thread count Superset would run upstream's main + IO thread loop at low io-threads and switch to its staged loop only from io-threads N up, with N found by benchmark (the same way the epoll-thread breakpoint is chosen). The 3-core gaps should close if upstream's loop performs the same inside superset. Superset's current 3-core wins would go with it (GET P16 1.36x, several P1 cells up to 1.23x), and switching modes on scale-up and scale-down would need its own tests.
B. Cut the staged loop's own costs at two threads Make the pieces in the profile cheaper: lane key prefetch per key, read events per client, lane entry and reply merge. Each is worth a few percent, so this means several iterations, and there is no guarantee it closes the 15% HSET P16 gap at 3 total CPUs.
C. Fix the 2-core cells on their own At io-threads 1 there are no lanes, and the remaining 3-6% gap is the per-command cost of the 8-bit keyspace split plus small extras. Run with no keyspace split at io-threads 1 and split the keyspace when scaling up. This targets only the 2-core cells and adds a reshard step to every scale-up.
D. Stop here Keep the two fixes as they are and leave the remaining cells below upstream as listed on this page.

Method and core layout

Builds
superset = fork superset-frontier 29152861a, run with --io-threads-free-on-bio yes --main-read-batch yes. upstream = 2a23bcda0 with default config. Both built with plain make on the server host from a git archive of the commit.
Hardware
c8g.metal-24xl server and a separate c8g.metal-24xl load generator in the same AZ, 0.11 ms round trip. The scale-up runs for fix 1 and the HSET and P1 scale-up cells used a second pair of the same type.
Load
memtier, 128 B values, 1M keys. 2, 3 and 4 total CPUs: 2,400 connections at P16 and 9,600 at P1. Pinned 1, 8 and 16 core layouts: 300 connections at P16 and 1,200 at P1. MSET10 sets 10 keys per command; throughput is commands/s for every workload.
2, 3, 4 total CPUs
Container model: NIC interrupts on CPU 0; main, IO threads and the background threads float over CPUs 1..N, io-threads = N. So 2 / 3 / 4 total CPUs = io-threads 1 / 2 / 3. Steady-state reps of about 25 s.
Scale-up
One server under constant load, with the CPU set and CONFIG SET io-threads changed together every 30 s: 2 → 3 → 4 → 3 → 2 total CPUs. Each step's level is the server-side rate over the step, recorded to 0.01M ops/s, so very small CI95 values are limited by that rounding.
1, 8, 16 total CPUs
Pinned layouts from the core-layout spec: 1 = main+irq+aux (io-threads 1); 8 = 3x irq, main, 3x io, aux (io-threads 4); 16 = 5x irq, main, 9x io, aux (io-threads 10).
Statistics
3 reps per arm, arm order rotated each rep. Mean ± CI95 (Student t, n − 1). The ratio's range divides the low end of one CI by the high end of the other, and the high end by the low end.
